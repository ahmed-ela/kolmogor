# Google workspace accounts

In the Mac app, open **Settings → Account → Manage account**. Google signs you in through the system browser. **Connect all accounts** walks through Codex CLI, Claude Code, Antigravity CLI, and Google in your remote Chrome profile. You can also open each connection individually. Provider subscriptions, device approvals, and two-factor authentication belong to the provider.

Codex CLI uses OpenAI’s device-code flow. If OpenAI reports that it is disabled, the account owner can enable device-code sign-in in ChatGPT’s Security settings, then return to **Connect**. Claude Code uses its own authorization page. Antigravity CLI opens Google’s personal-account consent flow. Enter the code from Google’s Antigravity confirmation page in the account window. Its worker checks the authenticated model catalog and keeps its credentials in its own persistent home. Remote Chrome opens Google’s sign-in page in the workspace and preserves the current verification step when reopened. Kolmogor shows Chrome as connected after it sees the signed-in Google Account menu.

## Account and workspace boundaries

The gateway verifies Google's signed ID token, audience, nonce, verified email and browser-bound, single-use state. The Google subject identifies the workspace. The email is used for display and pilot admission. The Mac exchanges a one-minute, single-use ticket with a per-attempt PKCE verifier. Its dedicated WebKit store receives an HTTP-only, Secure, SameSite session cookie. The account window has no agent bridge. Signing out revokes that session. Existing provider connections belong to the remote workspace and persist across Kolmogor sign-ins.

U01 hosts the account process under its own unprivileged system user. A restricted Unix socket accepts the fixed workspace operations in [broker.py](broker.py). Only the broker operates Kubernetes. It chooses the CLI executable, arguments, pod, display endpoint and provisioning templates. Each workspace receives a separate namespace, PVCs for the two CLI accounts and browser profile, a display credential, network policies and quotas. The capacity default is four workspaces on one node. Set `MAX_WORKSPACES` on the broker when the host has sufficient backing resources. PVC storage requests track allocations. Enforce filesystem quotas on the backing storage before offering untrusted tenants a hard disk usage guarantee.

Codex uses its device approval flow. Claude opens its official sign-in page and accepts its authorization code. Chrome runs with a real X display. Its viewer requires the owner's current Kolmogor session and an exact-origin WebSocket request. Viewer connections expire after 15 minutes and recheck the session after logout. Signing in to a Google website in that browser is independent of Kolmogor authentication. Chrome browser Sync is a separate product capability.

## Workspace chats

The **Chats** section in the iOS workspace and the Mac **Manage account** window opens the same account-owned history. Choose **New chat**, send a message, and open it again from **All chats**. The first message creates the chat. A workspace starts with an empty list. Existing desktop chats and third-party transcripts stay local until an explicit import is implemented.

U01 runs one account service and one private SQLite database in WAL mode on durable node storage. The `workspace_chats` and `workspace_turns` tables use the server-derived workspace identity. Reads, pagination, and continuation check ownership. Store the chat title, prompts, replies, send receipts and provider-thread binding there. Each connected provider runs in its own isolated CLI worker. Its persistent volume holds its credentials and provider sessions. Keep backing up both the SQLite file using an online SQLite backup and the workspace PVC. Stopping a phone or refreshing the page does not cancel an accepted turn.

The workspace streams Codex's answer text from its private app-server transport. The worker accepts answer deltas only for the acknowledged thread, turn and final-answer item. A signed-in client can subscribe to its own active turn over Server-Sent Events. Reconnecting starts with a snapshot of the current preview and continues the same job. The account service commits the final reply to SQLite after the worker confirms completion. Interrupted previews are discarded.

When upgrading an existing workspace, apply the updated Codex pod manifest before starting the new broker. The CLI pod mounts the same account and session volume at an additional path with read-only empty configuration and rules for chat inference. Its normal interactive configuration remains available at the original path.

The workspace picker groups models by provider. Codex lists every selectable model for the remote Codex login and shows its plan. To use another subscription, open **Connections → Codex CLI → Switch account** and authorize the new login on OpenAI’s device page. Gemini lists the Google models and reasoning levels available through the workspace’s Antigravity CLI connection.

Within a provider, the next message resumes the bound CLI session. Switching providers starts a new provider session in the same Kolmogor chat and includes recent completed exchanges from that chat. Transfers are limited to 32 KiB and 64 exchanges. The transfer marks omitted or shortened history, while the complete transcript stays in SQLite. Gemini checks the selected model and effort in its ACP session before dispatch and runs with a conversation-only agent. Completed replies retain their model and reopening restores the last successful choice.

The broker exposes fixed chat and model-list operations. The phone can supply message text, an optional model ID and a request ID. Only the service chooses the provider thread and only the broker chooses the executable and pod. A retry with the same request ID returns the original receipt. An interrupted service records an unconfirmed send and never automatically resubmits it. The pilot runs a single account-service writer. Moving to multiple account-service replicas requires coordinated dispatch/recovery and shared storage.

## Install on the workspace node

1. Deploy the [K3s workspace](../k3s/README.md), its gateway, seccomp profile and pinned worker images. Install Node 24 at `/opt/node-runtime` and install `cloudflared` from Cloudflare's signed package repository.
2. In the standalone Google Cloud project `kolmogor`, create an external Google Auth application using the basic identity scopes `openid email`. Use a **Web application** client with redirect `https://accounts.kolmogor.com/oauth/callback`. The optional development callback is `http://127.0.0.1:8786/oauth/callback`. Download the client JSON on the administrator's machine and transfer it over an authenticated channel to `/etc/kolmogor-accounts/google-web.json` on the node. Use SSH standard input or SFTP to a private staging file, then install it on the node and remove the staging copy. Hypervisor guest-exec wrappers can place even base64-encoded stdin in process arguments. Use them only for commands and paths during credential installation. Keep credentials out of Git, app bundles, logs and command-line arguments.
3. Create a dedicated named tunnel under the Cloudflare account that owns `kolmogor.com` and route **only** `accounts.kolmogor.com` to it. Transfer only its tunnel-specific credentials to `/etc/kolmogor-accounts/tunnel.json`, owned by root with mode 0600. The installer writes the hostname and loopback origin to its ingress configuration.
4. In the root-owned `/etc/kolmogor-accounts/pilot.conf`, set `PILOT_EMAILS` to a comma-separated list of approved Google email addresses. Add those people to Google Auth Platform's test audience as needed. To deliberately open verified-Google signup after the pilot, configure Google's production audience, size the node, and set `WORKSPACE_SIGNUP=public`.
5. Copy the tracked `accounts/` and `k3s/` directories into the root-owned `/opt/kolmogor-workspace/` tree. Run `/opt/kolmogor-workspace/accounts/install` as root. It provisions the service user, builds the pinned static assets, and installs the systemd units. The account service listens on node loopback. Google credentials stay on the node. The tunnel unit receives a private copy of its own credential through systemd.
6. Confirm `systemctl is-active kolmogor-{broker,accounts,account-tunnel}` and `curl -fsS https://accounts.kolmogor.com/api/me` (signed-out result: `{"email":null}`). Use **Manage account** in the installed app for the full sign-in check. Verify the provider's own status after each approval.

Back up the account database, broker allocation directory, cluster workspace Secrets and PVCs using an encrypted, access-controlled backup. Keep the Google client secret and tunnel credential in the operator's credential system. A restart preserves the account database and provider state. Pending provider handshakes may require starting sign-in again.

## Checks

From this directory run `npm ci`, `npm test`, `python3 -m unittest discover -s tests -p 'test_*.py'`, `npm run build`, and `npm audit`. Run `npm run test:browser` with an installed Chrome (or set `CHROME_BIN`) for a complete fixture walkthrough through the browser UI. The identity tests use a disposable database. The HTTP tests cover authorization, origin checks, native handoff, and sign-out. The broker tests cover ownership namespace validation, admission capacity, allowed operations, and the official provider authorization URLs.
